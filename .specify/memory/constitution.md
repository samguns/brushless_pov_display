# pov_leds Constitution

## Core Principles

### I. PIO-First LED Drive
All timing-critical LED column output must be driven by RP2040 PIO state machines, not by CPU bit-banging. Pixel data flows through a DMA → TX FIFO → PIO pipeline. The CPU's job is to prepare frame buffers and configure DMA; the PIO's job is to clock bits with cycle-accurate precision. No blocking loops in the critical output path.

### II. Timing Precision is Non-Negotiable
POV image quality depends entirely on column timing accuracy. Every column strobe interval must be derived from the measured rotation period of the display. The jitter budget for column switching is < 1 µs. Timer alarms and PIO clock dividers must be computed from `clock_get_hz(clk_sys)` at runtime, not hardcoded magic numbers. Hardcoded frequencies (e.g., `125000000`) are forbidden outside of early prototypes.

### III. Hardware Abstraction
Driver code (PIO programs, GPIO setup, DMA channels) must be separated from display logic (frame buffer management, image encoding, rotation mapping). Hardware-specific code lives in dedicated source files (`hw_led.c`, `hw_rotation.c`, etc.). Display logic must be testable without hardware by substituting a mock output function.

### IV. Minimal and Deterministic Memory Use
The target is an RP2040 with 264 KB SRAM and 2 MB flash. Rules:
- Frame buffers are statically allocated; `malloc` is forbidden in the display path.
- No heap allocation inside interrupt handlers or PIO feed loops.
- Total static RAM budget must be tracked and documented in the feature spec for any change that adds or resizes buffers.

### V. Single-Command Build and Flash
The project must build cleanly from a cold clone with one command (`ninja -C build`). All SDK and toolchain dependencies are pinned (Pico SDK 2.2.0, ARM toolchain 14_2_Rel1, picotool 2.2.0-a4). CMakeLists.txt is the single source of truth for build configuration; no out-of-band scripts are required for a normal build.

## Hardware Constraints

The target board is **Raspberry Pi Pico W** (RP2040, dual Cortex-M0+, 125 MHz, 264 KB SRAM, 2 MB flash, CYW43 Wi-Fi chip on SPI).

- GPIO assignments must avoid pins used by the CYW43 driver (GPIO 23, 24, 25, 29).
- PIO programs must account for both pio0 and pio1 being available; program placement must be explicit, not assumed.
- The default LED (GPIO 25 on Pico, CYW43 on Pico W) requires `PICO_DEFAULT_LED_PIN` guards as demonstrated in the existing code.
- USB stdio is currently disabled (`pico_enable_stdio_usb 0`); UART stdio is also disabled. Any debug output strategy must be decided and documented per feature.

## Development Workflow

- **Build**: `ninja -C build` from the workspace root.
- **Flash**: Use picotool (`picotool load <uf2> -fx`) or the VS Code "Run Project" task.
- **Debug output**: Decide per feature whether to enable USB or UART stdio; document the choice in the feature spec. Never leave stdio enabled in a release build without justification.
- **PIO programs**: Authored in `.pio` files; headers are generated by `pico_generate_pio_header` at build time. Never hand-edit generated `*.pio.h` files.
- **Code review**: All changes to the PIO program or DMA configuration require a timing analysis comment explaining the cycle budget.

## Governance

This constitution supersedes any conflicting guidance in README files or inline comments. Amendments require updating this file with an incremented version and a brief rationale comment. Any change that alters a Core Principle is a MAJOR version bump; new sections or principles are MINOR; clarifications are PATCH.

All feature specs and plans must include a "Constitution Compliance" section noting which principles apply and how they are satisfied.
